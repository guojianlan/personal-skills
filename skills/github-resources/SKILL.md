# GitHub 个人资源

这是跨项目云端供应商与远程服务的补充入口，不绑定当前业务项目。项目自身配置优先，包括本机服务、项目 Docker，以及通过项目配置接入的云端模型和远程服务。用户没有指定供应商或没有提到已有配置，不代表项目缺少配置；先完成下方检查，再决定是否使用资源库。资源库是普通私有 GitHub 仓库，当前存明文；公开 Skill 库只保存工具和虚构示例。

## 触发前：检查并验证项目配置

1. 先确定当前项目与任务需要的能力，检查相关配置文件（如 `.env`、`.env.local`、对应环境配置、应用配置、Docker Compose）及代码中的配置加载入口。核对环境变量覆盖、启动参数和运行环境，确定实际使用的端点、模型与凭据来源；`.env.example` 或变量名存在不代表已经配置。只检查当前项目与本任务相关的配置，不打印密钥或含密码的连接串。
2. 对已有配置做与任务匹配的最小可用性验证，优先复用项目现有客户端或检查命令，确保使用相同的配置加载链路。模型使用一次低成本、无业务数据的最小调用；数据库使用只读连通查询；其他服务使用能验证所需能力且无业务副作用的检查。只读到配置、健康端点成功或获取模型列表，不能证明目标模型或业务接口可调用。可复用本轮同一配置、环境与能力下已完成的真实验证，无需重复请求。
3. 配置可用且覆盖当前需求：直接复用，结束资源库选用流程；不运行资源库扫描、读取库内凭据、导出配置或切换供应商。仅修改提示词、排序逻辑或业务代码，不因涉及模型就触发本 Skill。
4. 配置缺失或未覆盖新增能力：仅为缺失部分进入资源库选用流程。验证失败时先排查配置加载、变量映射、服务启动、网络、认证、权限和模型名称；在任务授权内修复后复验，不因一次超时就改用资源库。经排查确认现有配置不可用且任务允许替代时，才查询库内候选；查询候选不等于授权覆盖原配置或迁移供应商。
5. 无法执行验证时明确报告“未验证”及原因，不把未知判为不可用，也不据此自动触发资源库。用户明确要求查询、维护资源库或使用库内指定资源时，可直接处理该请求；实际接入仍需核对项目配置和用户约束。

## 入口

本 Skill 仅依赖 Python 3.9+ 与 GitHub CLI。把下面 `<skill>` 替换为本 Skill 的绝对目录；不要依赖当前工作目录。

```sh
python3 <skill>/scripts/github_resources.py capabilities
python3 <skill>/scripts/github_resources.py search <能力或用途>
python3 <skill>/scripts/github_resources.py show <准确资源ID>
```

仓库优先级：`--repo owner/repo`、`GITHUB_RESOURCES_REPO`、本机绑定、当前账号的 `personal-resources`。不必每个项目重复指定。新设备先 `gh auth login --hostname github.com --git-protocol https --web`；账号授权由 gh 管理，不能把 Token 发到聊天或复制登录文件。需要自定义目标时运行 `bind owner/repo`。本机绑定位于 `~/.config/github-resources/config.json`，可由 `GITHUB_RESOURCES_CONFIG` 覆盖；绑定只存账号和仓库。

## 默认选用流程

1. 仅在满足上述触发条件后，从任务与代码识别待补充的外部能力，无需供应商关键词。首次库内选型运行 `capabilities`：一次返回完整能力分组、配置、文档和验证状态。准确 ID 已知时直接 `show`，不重复 `status → 搜仓库 → 搜名称 → 逐篇读 Markdown`。已得到的本轮能力总览可复用，实际导出/写入仍在线检查。
2. 优先级：用户明确指定的来源与约束 → 项目已验证可用的配置与契约 → 库内符合任务的资源。需要从库内补充时，按必要能力、环境/区域/权限、已验证经验、用户偏好、成本和延迟比较。未知信息标为未知，不编造“最便宜”。不擅自迁移项目既有供应商，不因库里存在生产凭据就用于开发。
3. 用一句话说明选择与理由，例如“这次使用已有的实时语音资源，因为需要双向流式对话；纪要复用现有文字模型”，随后继续实施，不把已能判断的选型变成确认问题。只在没有适用资源、授权失效、缺失信息会改变正确性或后果时询问最少必要问题；不要默认寻找新的供应商、注册账号或购买服务。用户明确指定其他来源时遵从其指定。
4. 阅读选中资源的官方文档并核对项目协议。模型列表是维护快照；供应商发现接口返回的模型不等于当前 Key 已验证能调用。STT/TTS/Realtime 依对应接口范围维护。按产品需要组合能力，避免对已覆盖语音输入输出的 Realtime 无意义叠加 STT/TTS。本机服务与项目 Docker 按项目自身配置使用，不导入本库。
5. 需要凭据时用 `export` 写本地文件，不先打印 catalog 或秘密原文。映射是一个 JSON 文件，例如 `{"LLM_API_KEY":"secrets.api_key","LLM_BASE_URL":"config.base_url","LLM_MODEL":"config.default_model"}`。

```sh
python3 <skill>/scripts/github_resources.py export <准确资源ID> \
  --map-file /absolute/path/mapping.json --output /absolute/path/.env.resources
```

输出默认拒绝覆盖、拒绝符号链接，POSIX 上以 0600 保存。生成的是字面量 dotenv，不能直接当 shell 脚本执行；Docker Compose、特殊 SDK 或引号密码需按其解析规则适配。先检查目标是否被 Git 忽略；不把凭据写入前端、公开仓库、日志、截图或聊天。更改既有环境文件前保留其他配置，不能用整文件覆盖代替合并。工具不会自动提交业务项目。

6. 用户要入口时返回工具提供的 GitHub 文件链接或记录中的服务/文档链接。`catalog.json` 的网页包含真实凭据，只有有仓库权限的账号可读；不要把这个链接描述为无凭据的公开说明页。不得将含密码的数据库连接串做成聊天链接。
7. 做与需求匹配的最小验证。现有开发授权可涵盖必要的测试调用；不要因查到密钥就发邮件、部署、改生产数据或运行无关请求。报告配置完成与真实调用通过的区别。

## 自动沉淀与能力升级

遵循用户已明确启用的自动维护约定：在实际使用库内资源的开发任务结束后，自动把本次实际确认的协议、模型发现范围、SDK/环境变量适配、限制、失败原因、验证时间和来源写回私有资源库；无需再次要求“记下来”。仅复用项目配置时不触发资源库写回，也不自动将项目凭据导入库内。使用 `record` 只更新元数据并保留真实凭据，不用脱敏的 `show` 输出替换完整资源。命令与格式见 [资源格式与维护](references/catalog.md)。

区分官方文档描述、模型列表发现、配置加载成功与真实调用通过；只有真实完成的检查才能升级相应验证状态。失败记录限定模型、区域、参数和时间，不把一次超时概括为整个服务不可用。不重复写入已有观察，不在经验里保存请求正文、候选人数据或秘密。`capabilities` 每次从已维护事实自动生成最新能力总览。

这里的升级包括补齐资源知识、确认新增可用模型、改进适配经验与提出有依据的更好组合；它不自动购买套餐、替换全局默认模型、轮换密钥、添加未授权账号或迁移生产系统。新方案先有文档或验证证据，再记录建议；实际切换按任务和用户约束执行。普通无关问答不运行资源扫描或写入，纯查询没有新事实时不提交空更新。

明确维护凭据/地址/默认设置时才用 `put --file`，先读当前版本保留无关字段。所有更新携带当前 `catalog_sha`；冲突重新读取核对，不强制覆盖。超时或结果未知先检查远程，不盲重试。不要从其他项目或设备无边界搜集凭据。

全部工具每次读取/写入都检查仓库私有权限；同一账号可以跨设备读取，不能因找不到资源降级到公开仓库。不自动改仓库可见性，不复制 gh 凭据。Skill 不提供密码加密、生产部署或后台同步。
